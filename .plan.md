## Implementation Steps

### Step 1: Create Models (`workload/models.py`)

Define core dataclasses following existing patterns from `benchmark/results.py`:

```python
class WorkloadProfile(Enum):
    READ_HEAVY = "read_heavy"      # 90% reads, 10% writes
    WRITE_HEAVY = "write_heavy"    # 20% reads, 80% writes
    MIXED = "mixed"                # 50% reads, 50% writes
    ANALYTICS = "analytics"        # 100% reads, complex queries
    INGESTION = "ingestion"        # 100% writes, timeseries append

@dataclass
class QueryStep:
    query_id: str
    repeat: int = 1
    think_time_ms: int = 0
    batch_size: int | None = None
    concurrent: bool = False

@dataclass
class WorkloadScenario:
    name: str
    description: str
    profile: WorkloadProfile
    paradigms: list[str]
    sequence: list[QueryStep]
    duration_seconds: int | None = None
    loop: bool = False
    collect_throughput: bool = True
    collect_latency_distribution: bool = True
    collect_error_rate: bool = True

@dataclass
class QueryStats:
    query_id: str
    executions: int
    successes: int
    failures: int
    # Latency
    latency_p50_ms: float
    latency_p95_ms: float
    latency_p99_ms: float
    latency_avg_ms: float
    latency_max_ms: float
    # Memory (per-query compilation)
    memory_peak_avg_mb: float    # Average peak across executions
    memory_peak_max_mb: float    # Max peak observed
    memory_peak_total_mb: float  # Sum = resource impact of this query type

@dataclass
class WorkloadResult:
    scenario_name: str
    paradigm: str
    # Throughput
    total_queries: int
    total_duration_seconds: float
    qps: float
    # Latency (global)
    latency_p50_ms: float
    latency_p95_ms: float
    latency_p99_ms: float
    latency_max_ms: float
    # Errors
    total_errors: int
    error_rate: float
    # Memory
    scenario_memory_peak_mb: float              # Global peak during scenario
    query_memory_breakdown: dict[str, float]    # query_id -> total memory impact
    # Per-query breakdown
    query_stats: dict[str, QueryStats]
```

### Step 3: Create Executor (`workload/executor.py`)

Main execution engine:

```python
class WorkloadExecutor:
    def __init__(
        self,
        paradigm: str,
        configs: dict,
        isolation: IsolationManager,
    ):
        ...

    def run_scenario(
        self,
        scenario: WorkloadScenario,
        on_progress: Callable | None = None,
    ) -> WorkloadResult:
        """Execute workload with duration/loop control."""

    def _execute_step(
        self,
        step: QueryStep,
        executor: QueryRunner,
    ) -> list[StepResult]:
        """Execute single step with repeat and think_time."""

    def _collect_metrics(
        self,
        results: list[StepResult],
    ) -> WorkloadResult:
        """Aggregate into final metrics with percentiles."""
```

Key behaviors:
- NO reset between queries (persistent state)
- Use `time.sleep()` for think_time
- Loop sequence until `duration_seconds` if `loop=True`
- Collect all latencies for percentile calculation
- Track errors without crashing

### Step 4: Create Predefined Workloads (YAML)

Create 5 YAML files in `config/workloads/`:

1. **dashboard_refresh.yaml** - Read-heavy (90/10)
   - Q12 initial load, then Q6/Q7/Q13 refresh cycles
   - 5 second think time between refreshes
   - 5 minute duration, looped

2. **iot_ingestion.yaml** - Write-heavy (20/80)
   - QW1 timeseries append in batches of 100
   - Occasional QW2 metadata updates
   - 1 minute duration, looped

3. **mixed_middleware.yaml** - Mixed (50/50)
   - Alternating write batches and read queries
   - QW1 → Q1 → Q8 → QW1 → Q7
   - 3 minute duration, looped

4. **bos_twin.yaml** - BOS digital twin simulation
   - Graph context navigation (traversées FEEDS/SERVES)
   - High-frequency timeseries ingestion (~350 queries/s)
   - Concurrent dashboard queries
   - Simulates in-memory graph middleware typical usage (128GB+ RAM context)
   - 2 minute duration, looped

5. **graph_stress.yaml** - Graph-intensive workload
   - Deep traversals (Q1-Q5, Q20-Q23)
   - Tests graph engine under sustained structural load
   - No timeseries, pure graph queries
   - 3 minute duration, looped

6. **timeseries_stress.yaml** - Timeseries-intensive workload
   - Heavy aggregations (Q6 time_bucket, Q7 drift detection)
   - Unwind/expand operations (M1 TimeseriesChunk traversal)
   - Sliding window analytics (Q9, Q10, Q11)
   - Tests TimescaleDB vs in-memory TS performance
   - 3 minute duration, looped

## Key Design Decisions

### 1. No RAM Gradient
Workloads run at fixed RAM (system default or user-specified). Unlike simple benchmarks, we don't vary RAM per run.

### 2. Persistent State
Unlike simple benchmarks that reset between queries, workloads maintain database state throughout the sequence to simulate realistic usage.

### 3. Query Execution Reuse
Leverage existing `QueryRunner` protocol and paradigm-specific runners. The `WorkloadExecutor` wraps these runners with timing/looping logic.

### 4. Results Format
Similar to `BenchmarkResults` but focused on throughput metrics:
- QPS (queries per second) as primary metric
- Latency distribution (p50/p95/p99/max)
- Error rate and per-query breakdown

### 5. Memory Measurement Strategy
Unlike simple benchmark (reset memory.peak between each query), workloads use:

**Option A - Global scenario measurement:**
- Reset peak before scenario start
- Read peak after scenario end
- Simple but less granular

**Option B - Per-query compilation (RECOMMENDED):**
- Reset peak before EACH query execution (like simple benchmark)
- Aggregate memory peaks per query_id across all executions
- Result: `query_stats[query_id].memory_peak_avg_mb`, `memory_peak_max_mb`
- Shows which query types consume most memory in the workload

This provides richer analysis: "Q12 consumes 2GB peak while Q6 only 200MB" even within a mixed workload.

The `WorkloadResult` includes:
```python
@dataclass
class QueryStats:
    # ... existing fields ...
    memory_peak_avg_mb: float   # Average peak across all executions
    memory_peak_max_mb: float   # Maximum peak observed
    memory_peak_total_mb: float # Sum of all peaks (resource impact)

@dataclass
class WorkloadResult:
    # ... existing fields ...
    scenario_memory_peak_mb: float  # Global peak during entire scenario
    query_memory_breakdown: dict[str, float]  # query_id -> total memory impact
```

### 6. Integration Points
- Uses existing `IsolationManager` for container lifecycle
- Uses existing `QueryCatalog` for query definitions
- Uses existing paradigm connection configs
- Exports JSON results to same `data/results/` directory
